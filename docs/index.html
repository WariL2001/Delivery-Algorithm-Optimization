Delivery Route Optimizer

How much faster can a delivery route be computed with the right algorithm? We implemented and benchmarked five routing algorithms on the real New York City street network, from naive search to optimized shortest-path and route-ordering strategies.

The Problem

Every delivery company has to answer two questions, thousands of times a day.

1. What is the shortest path from A to B?

Given a real street network, find the fastest route between two locations, such as a restaurant and a customer. This is the shortest-path problem, which can be solved efficiently.

2. In what order should the stops be visited?

With several deliveries, the driver must choose the order of stops. This is a version of the Traveling Salesman Problem (TSP), which is NP-hard: the number of possible orders grows factorially.

Our project compares how different algorithms handle each question, and shows the difference between an inefficient algorithm and a problem that is computationally hard.

Our Solution

A two-stage routing pipeline built and benchmarked from scratch.

  1. Load the city as a graph

    The NYC street network is converted into an adjacency-list graph.

  2. Compute shortest paths between stops

    BFS, Dijkstra, and A* each find routes between delivery points, and we compare their speed and the number of nodes they explore.

  3. Choose the order of deliveries

    Brute-Force finds the optimal order for small sets of stops; Nearest Neighbor finds a fast approximate order for larger sets.

  4. Benchmark and visualize

    Every algorithm is timed across increasing input sizes, and routes are drawn on an interactive map.

Algorithms

All core algorithms were implemented by the team, not called from a library.

Stage 1: Shortest path (A → B)

Baseline

Breadth-First Search

Explores the graph level by level. Finds the path with the fewest street segments, but ignores distance, so it is not optimal on a weighted map.

Efficient

Dijkstra's Algorithm

Uses a priority queue to always expand the closest unvisited node. Guarantees the shortest path when all edge weights are non-negative.

Optimized

A* Search

Dijkstra guided by a heuristic (straight-line distance to the goal). Still optimal with an admissible heuristic, but explores far fewer nodes.

Stage 2: Delivery order (multi-stop)

Exact

Brute-Force Route Search

Tries every possible order of stops and keeps the cheapest. Always optimal, but only feasible for a small number of stops.

Heuristic

Nearest Neighbor

Greedy strategy: always drive to the closest unvisited stop next. Very fast, but the resulting route is not guaranteed to be optimal.

Complexity

V = intersections (nodes), E = street segments (edges), n = number of delivery stops.

Algorithm Time Space Optimal?
BFS O(V + E) O(V) Only on unweighted graphs
Dijkstra (binary heap) O((V + E) log V) O(V) Yes (non-negative weights)
A* (binary heap) O((V + E) log V) worst case O(V) Yes (admissible heuristic)
Brute-Force (TSP) O(n! · n) O(n) Yes
Nearest Neighbor (TSP) O(n²) O(n) No (approximation)

Stage 2 complexities assume the distances between stops are already computed by a Stage 1 algorithm. Full derivations are in the technical paper.
